# A 平台 — 後端基礎設施實作計劃書

> 版本：v0.1
> 範圍：搭建 XRPL 後端服務基礎設施 + 極簡示意前端
> 目標：把主辦方要求的五大必備技術封裝成可重用的服務層，讓後續業務邏輯（帳號、用戶互動、市場撮合等）能在此之上開發
> 技術選型：TypeScript / Node.js / xrpl.js / xumm-sdk

-----

## 一、本計劃的定位與邊界

這份計劃**只做基礎設施**，不做業務邏輯。

具體來說，做完這個階段後，會有一組「能直接呼叫的 XRPL 能力」，例如「幫某帳號建立 Trust Line」、「發行 N 個 A 幣」、「掛一張 DEX 賣單」、「建立一個條件式 Escrow」。這些能力被包成乾淨的 service 函式與 REST API，前端團隊或後續業務開發者拿到後，不需要懂 XRPL 細節就能組裝功能。

**做（in scope）**

- XRPL 連線管理與設定
- 五大技術元件的 service 封裝
- 對外的 REST API 介面
- Xaman 簽署流程的後端串接
- 一個極簡前端示意頁（驗證流程能跑通用）

**不做（out of scope，留給後續）**

- 帳號登入註冊系統
- 資料庫與用戶資料持久化
- 訂單撮合、SCU 換算等業務邏輯
- 正式前端 UI（由前端團隊負責）

-----

## 二、為什麼這樣切分

後端基礎設施先行的核心價值，是先把「最不確定、最需要試錯」的部分驗證掉。

XRPL 的操作（特別是 Escrow 與 Xaman 簽署）跟一般 Web2 開發差異大，與其等業務邏輯定案再一起開發、出錯時難以定位問題，不如先把這層獨立打穩。等基礎設施能穩定運作，業務邏輯就只是「組合這些積木」，開發風險大幅降低。

對前端團隊而言，他們拿到的是一份清楚的 API 契約，可以平行開發，不必等你把整個系統做完。

-----

## 三、五大技術元件 → 服務層對應

主辦方要求的五項必備技術，各自封裝成一個 service 模組：

|必備技術                   |Service 模組         |對外提供的核心能力             |
|-----------------------|-------------------|----------------------|
|Trust Lines            |`trustline.service`|建立 / 查詢帳號與發行方之間的授權關係  |
|Issued Assets (IOU/MPT)|`asset.service`    |發行 A 幣、查詢餘額、轉移        |
|DEX 整合                 |`dex.service`      |掛單 / 撤單 / 查詢市場深度 / 查成交|
|Xaman Wallet           |`xaman.service`    |產生簽署請求、輪詢簽署結果、廣播交易    |
|XLS-100 Smart Escrow   |`escrow.service`   |建立 / 完成 / 取消條件式託管     |

每個模組對外暴露的是「業務語意」的函式（例如 `issueToken(amount, destination)`），內部才處理 XRPL 的交易組裝細節。這樣業務開發者讀得懂、用得順。

-----

## 四、系統分層架構

由下而上分四層，職責清楚分離：

**1. XRPL 連線層（infrastructure）**
管理與 XRPL 節點的連線（Testnet 階段用公開節點），統一處理連線重試、交易廣播、結果查詢。所有 service 共用這一層，不各自連線。

**2. Service 層（五大模組）**
上面那張表的五個模組。這層只懂 XRPL，不懂 HTTP，方便單獨測試與被任意呼叫。

**3. API 層（controller / routes）**
把 service 包成 REST 端點，處理參數驗證、錯誤格式化、回應結構統一。前端只跟這層溝通。

**4. 示意前端**
一個極簡頁面，用來驗證每個 API 真的能跑通，也作為交付給前端團隊的「行為參考範例」。

┌─────────────────────────────┐
│   示意前端（驗證 + 範例）      │
└──────────────┬──────────────┘
               │ HTTP / JSON
┌──────────────▼──────────────┐
│   API 層（REST routes）       │
└──────────────┬──────────────┘
               │ 函式呼叫
┌──────────────▼──────────────┐
│   Service 層（五大模組）       │
└──────────────┬──────────────┘
               │ xrpl.js / xumm-sdk
┌──────────────▼──────────────┐
│   XRPL 連線層 + Xaman 串接     │
└──────────────┬──────────────┘
               │
        XRPL Testnet

## 五、技術棧

|層級       |選型                          |說明                          |
|---------|----------------------------|----------------------------|
|執行環境     |Node.js + TypeScript        |全程型別保護，AI 輔助開發較穩定           |
|Web 框架   |Express（或 Fastify）          |輕量、生態成熟、MVP 友善              |
|XRPL SDK |xrpl.js                     |官方主力維護，文件最完整                |
|Xaman SDK|xumm-sdk                    |Xaman 官方 SDK，無 Python 等價物   |
|設定管理     |dotenv                      |管理節點 URL、發行方錢包、Xaman API key|
|示意前端     |單頁靜態 HTML + fetch（或最小 React）|純驗證用途，不投入設計                 |

框架用 Express 還是 Fastify 兩者皆可，差異不大；若團隊沒特別偏好，Express 範例最多、AI 最熟。

## 六、開發階段規劃

按依賴順序排，每個階段都有可驗證的產出，不會做到一半卡住。

### 階段 0：專案骨架與連線層

- 建立 TS 專案、目錄結構、設定管理
- 實作 XRPL 連線層，能連上 Testnet、查到帳號資訊
- **驗證點**：跑一個腳本，印出某個 Testnet 帳號的餘額

### 階段 1：發行方錢包與資產發行

- 準備發行方帳號（Testnet faucet 取得）
- `trustline.service`：讓一個測試帳號對發行方建立 Trust Line
- `asset.service`：發行 A 幣到該帳號、查餘額
- **驗證點**：A 幣成功發行，鏈上可查到餘額

### 階段 2：Xaman 簽署流程

- `xaman.service`：產生簽署請求 → 取得 QR / deeplink → 輪詢結果 → 廣播
- 這是整個基礎設施最關鍵也最特別的一段（非託管簽署）
- **驗證點**：手機 Xaman app 掃碼，簽署一筆交易並成功上鏈

### 階段 3：DEX 整合

- `dex.service`：掛 A 幣 / XRP 賣單、查市場、查成交
- **驗證點**：在 Testnet DEX 上掛單成功，能查到掛單狀態

### 階段 4：XLS-100 Smart Escrow

- `escrow.service`：建立條件式託管、完成釋放、條件未達取消退回
- **驗證點**：完整跑一輪「鎖入 → 條件達成 → 釋放」與「鎖入 → 取消 → 退回」

### 階段 5：API 層與示意前端

- 把上述 service 全部包成 REST 端點
- 寫一個極簡前端，每個端點對應一個按鈕，點了能看到結果
- **驗證點**：前端點按鈕能完整走通五大元件的代表性操作

## 七、交付物

做完後交給團隊與前端的東西：

1. **可運行的後端 server** — 跑起來就提供五大元件的 REST API
1. **API 契約文件** — 每個端點的路徑、參數、回應格式（前端據此平行開發）
1. **示意前端** — 行為參考範例，前端團隊看了知道流程怎麼走
1. **環境設定範例** — `.env.example`，說明需要哪些 key 與設定
1. **README** — 如何啟動、如何取得 Testnet 帳號、Xaman 設定步驟

## 八、為後續業務邏輯預留的接口

這層基礎設施做完後，後續的業務功能要怎麼接上去，先說清楚方向，避免之後返工：

- **帳號登入註冊**：未來的用戶系統會在 API 層之上加一層認證中介層（middleware），service 層不需改動。XRPL 帳號本身可作為身份基礎，搭配 Xaman 做登入驗證。
- **資料持久化**：service 層目前直接讀寫鏈上，未來需要快取或業務資料（訂單紀錄、SCU 換算表）時，加一層資料庫存取，不影響 XRPL service。
- **業務邏輯（撮合、換算）**：會成為新的 service 模組，組合既有的五大基礎模組，而非重寫它們。

換句話說，這層的設計原則是**「業務無關、可被組合」**，後續一切都疊在上面，不回頭改地基。

## 九、待你確認的決策點

開始實作前，有幾個選擇會影響骨架，建議先定：

1. **Web 框架**：Express（範例多）還是 Fastify（效能好）？
1. **Issued Asset 類型**：先用傳統 IOU，還是直接上 MPT（Multi-Purpose Token）？MPT 較新、功能強，但範例較少。
1. **示意前端形式**：純 HTML + fetch（最快），還是最小 React（跟前端團隊技術一致，可當範例）？
1. **發行方錢包管理**：MVP 階段私鑰放 .env 即可，但要先講好正式環境怎麼處理（這也是評審可能會問的安全問題）。
