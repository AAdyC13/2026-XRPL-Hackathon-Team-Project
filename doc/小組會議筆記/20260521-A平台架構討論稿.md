# A 平台 — B 方向架構討論稿

> 版本：v0.1（討論用）
> 目的：作為團隊內部討論 B 方向（跨校 + 個體戶算力共享市場）的對齊文件。
> 性質：本文為**討論版**，多處保留開放選項，等待團隊決議後再收斂為定稿。

---

## 一、定位

A 平台從「校方算力分發站」升級為「跨校 + 個體戶的算力共享市場」。

A 平台在新架構下扮演**做市商與發行方雙重角色**：對外發行 A 幣作為算力憑證、撮合算力供需雙方、並透過 XRPL 內建 DEX 與 XLS-100 Smart Escrow 提供市場基礎設施。

對位 Ripple 2026 RWA 戰略：A 幣為「閒置 GPU 算力 → 代幣化 → 自由市場交易」的微縮實作，與 io.net、Render Network 屬同類賽道，但建構於 XRPL 之上。

---

## 二、市場結構

新架構引入三類角色，雙向互動：

### 2.1 角色定義

| 角色 | 子類別 | 行為 |
|---|---|---|
| 算力供給方 | 本校、他校、個體戶 | 提供 GPU 算力 → 換取 A 幣 |
| A 平台 | 唯一 | 發行 A 幣、撮合交易、運營 DEX 與 Escrow |
| 算力需求方 | 校內研究室、他校用戶、個體戶 | 持有 A 幣 → 換取算力使用 |

角色可互換：同一帳號可同時是供給方與需求方（例如某研究室白天賣閒置算力、晚上買其他高階卡使用）。

### 2.2 資金與算力雙向流動

- **供給側流入**：算力供給方提供算力 → A 平台鑄造對應 A 幣給供給方
- **需求側流出**：算力需求方付出 A 幣 → A 平台兌換為算力使用權
- **二級市場**：A 幣可在 XRPL DEX 自由交易，可與 XRP / RLUSD 形成交易對
- **私下交易**：透過 Xaman 錢包點對點轉移 A 幣

## 三、A 幣設計（待團隊決議）

### 3.1 計價單位

**核心問題**：跨校與個體戶提供的 GPU 規格不一（H100 / A100 / RTX 4090...），1 A 幣到底等於什麼？

**提案方向**：引入「標準算力單位（Standard Compute Unit, SCU）」作為記帳基礎。

- 1 SCU = 1 H100-hour（建議基準）
- A100-hour ≈ 0.6 SCU（待校準）
- RTX 4090-hour ≈ 0.3 SCU（待校準）
- **1 A 幣 ≡ 1 SCU**

待決議：
- [ ] 是否採用 SCU 模型？或有其他計價設計？
- [ ] 換算表是否需要動態調整？由誰維護？
- [ ] hackathon 階段是否只支援單一規格（簡化 demo）？

### 3.2 發行與銷毀機制

**提案方向**：算力憑證模型。

- **鑄造**：算力供給方質押算力承諾 → 鑄造對應數量 A 幣
- **銷毀**：算力需求方兌換算力 → 對應 A 幣銷毀
- **總量約束**：A 幣總供給 = 未交付算力承諾的總和

此設計的好處：
- A 幣始終 1:1 對應真實算力
- 不存在超發或無中生有
- 算力交付完成即自動完成貨幣回收，無需中央調控

待決議：
- [ ] 鑄造時是否需要先鎖定算力配額？鎖定週期多長？
- [ ] 若供給方違約（鑄了幣但不交付），如何處理已流通的 A 幣？
- [ ] 是否需要保留一部分 A 幣作為「平台儲備金」？

## 四、五大技術元件在新架構中的角色

對應原專題技術棧的五個元件，在 B 方向下各自承擔的職責：

### 4.1 Trust Lines
建立用戶與 A 平台之間的授權關係。任何要持有 A 幣的帳號都需先與 A 平台建立 Trust Line，這是 XRPL 上發行資產的基本要求。

### 4.2 Issued Assets
A 幣本身。以 IOU 或 MPT 形式發行，由 A 平台作為發行方。

### 4.3 DEX 整合
- A 幣 / XRP 交易對：提供外部接通與市場定價
- A 幣 / RLUSD 交易對（路線圖）：接通機構級穩定幣
- 為「不使用者」提供持有與套利動機，符合健全性驗證要求

### 4.4 Xaman 錢包
- 身份驗證與交易簽署
- 跨校用戶與個體戶的統一入口
- 點對點轉移 A 幣（私下交易）

### 4.5 XLS-100 Smart Escrow

**這是 B 方向最關鍵的元件**，承擔交易履約保證的角色。

主場景：**算力交易的條件式託管**
1. 需求方發起算力購買請求
2. A 幣鎖入 XLS-100 Escrow
3. 供給方提供算力服務（以算力使用日誌作為交付憑證）
4. 條件達成 → A 幣釋放給供給方
5. 條件未達成或違約 → A 幣退回需求方

延伸場景（路線圖）：
- 校方對研究室的免費配額（條件釋放、過期回收）
- 長期算力預訂（時間鎖）
- 研究合作的條件支付（成果交付才釋放）

## 五、健全性驗證對照

對照記憶第5條的四項條件：

| 條件 | B 方向是否通過 | 實現方式 |
|---|---|---|
| 雙向市場（角色互換或多方需求並存） | ✅ | 供給方、需求方角色可互換；多方並存 |
| 對「不使用者」有持有動機 | ✅ | 算力套利、DEX 投機、價格儲存 |
| 雙退出路徑（DEX + 發行方贖回） | ✅ | XRPL DEX 交易 + A 平台兌換算力 |
| XLS-100 程式化退出 | ✅ | 算力交易託管、條件式釋放 |
| **排除項**：封閉點數、單向兌換券 | ✅ 已排除 | A 幣可在開放市場流通 |

對位主辦方期待的「四層產品框架」：

1. **價值源頭**：✅ GPU 算力（H100/A100 等），具公開市場價值
2. **代幣表達**：✅ 1 A 幣 = 1 SCU，1:1 綁定真實算力
3. **橋接清算**：✅ A 幣 / XRP 交易對，XRP 作橋樑
4. **外部接通**：✅ 透過 XRP 接通 RLUSD 與外部市場（路線圖）

## 六、敘事與擴展路徑

提案敘事分三階段，呈現「可複製、可擴展」的故事弧：

| 階段 | 範圍 | 角色 | 用途 |
|---|---|---|---|
| MVP（hackathon demo） | 單校 | 本校 + 校內研究室 + 1~2 模擬個體戶 | 證明機制可運行 |
| 擴展期 | 跨校 | 多校方 + 跨校用戶 + 真實個體戶 | 證明可複製 |
| 終局 | 開放市場 | 任何個體戶、企業、機構 | 證明可擴展至 RWA 市場 |

## 附錄 A：B 方向新出現的問題與加固建議

從原始 B 方向構思（單純引入算力供給方）到完整可運作的市場，需要補上以下五個面向。本附錄為加固建議，不在主架構討論時必須全部處理。

### A.1 算力規格標準化

**問題**：跨校與個體戶提供的卡型不一，1 A 幣的對應價值如何統一？

**加固建議**：
- 採用 SCU 作為記帳單位（見 §3.1）
- hackathon 階段可簡化：只支援 H100（本校現有硬體），其他卡型寫進路線圖
- 換算表初期由 A 平台維護，後期可開放治理

### A.2 算力品質與履約保證

**問題**：個體戶賣的算力可能不穩定、可能不交付，誰來擔保？

**加固建議**：
- 主用 XLS-100 Escrow 做條件式託管（見 §4.5）
- 交付憑證可採：算力使用日誌、平台監控數據、用戶簽收
- 違約處理：A 幣自動退還 + 信譽扣分

### A.3 A 平台的中立性與信任

**問題**：A 平台成為市場做市商後，誰來運營？如何取得各方信任？

**加固建議**：
- 初期：由本校主導、聯合啟動校共同運營
- 中期：成立校際聯盟或基金會
- 長期：過渡到 DAO 治理（路線圖）
- hackathon 文件中**至少需交代治理方向**，不必完整實作

### A.4 A 幣的初始發行邏輯

**問題**：新增「賣算力換幣」入口後，總量如何控制？是否會超發或通縮？

**加固建議**：
- 採用鑄造-銷毀模型（見 §3.2）
- A 幣總供給 = 未交付算力承諾總和，自然平衡
- 若需平台儲備（應急、價格穩定），上限設為總供給的 X%（待定）

### A.5 個體戶可信度與准入

**問題**：任何人都能當算力供給方？如何防止劣質供給污染市場？

**加固建議**：
- 信譽分數系統（基於交易歷史）
- 接入時跑 benchmark 驗證宣稱規格
- 黑名單機制
- hackathon 階段：設計概念但不完整實作，列入路線圖

## 附錄 B：與評審可能問題的對應

評審常見問題及本架構的回應角度：

| 評審可能問題 | 回應角度 |
|---|---|
| A 幣為什麼需要上鏈？傳統資料庫不行嗎？ | 因為需要：(1) XLS-100 可程式化條件支付 (2) 跨機構流通 (3) 開放市場定價 |
| 誰會持有 A 幣但不用 API？ | 算力供給方收幣後待出售；投機者套利；研究室預訂未來配額 |
| 校方為何同意 A 平台這個中間層？ | A 平台提供：跨校算力調度、自動化結算、條件式履約、開放市場接通——這些是校方自建系統無法低成本實現的 |
| 個體戶為何信任 A 平台？ | XLS-100 託管保證履約；DEX 提供自由退出；非託管錢包（用戶持有私鑰） |
